磁盘空间不足，无法解压 ZIP、RAR 或 7z：解决办法

WinRAR、7-Zip 和 unzip 在解压完成之前都会把压缩包留在磁盘上，所以磁盘必须同时容纳压缩包和所有解压出的文件：一个 180 GB、解压后为 200 GB 的压缩包，总共要占用 380 GB。可以解压到其他磁盘、释放空间，或者就地解压，这样只需为解压出的文件预留空间。

作者 Yash Bavadiya，HatchZip 的开发者。更新于 2026-11-28。

为什么解压时要同时为压缩包和文件留出空间？

因为普通的解压只是把数据从压缩包中复制出来。解压过程中不会删除任何东西，压缩包会一直保留，直到你自己删除它。

要看的是解压后的大小，而不是压缩包本身的大小。在 WinRAR 或 7-Zip 中打开压缩包，把“大小”（Size）一列加起来，这就是解压要写入的数据量。“压缩后大小”（Packed 或 Packed Size）一列则是压缩包已经占用的空间。视频、音乐和大多数游戏数据几乎压缩不了，所以这两个数字往往很接近，这时磁盘总共需要将近压缩包两倍的空间。

报错信息是什么样的？

各个程序的措辞不同，但意思都一样：磁盘已满，写入失败。

  • Windows：“There is not enough space on the disk.”（中文版 Windows 显示为“磁盘空间不足。”）这是系统为错误 112 提供的文本，见 Microsoft 的列表（英文）；直接转述 Windows 错误的程序都会显示这条信息。
  • WinRAR：“Not enough disk space for”后接文件名，或者“Write error in the file”。这两条都是 WinRAR 7.13 中的提示。
  • Linux 和 macOS 上的 unzip：“write error (disk full?)”。
  • Linux 上的 7-Zip：“No space left on device”。

如果要解压到的磁盘明明有足够空间，那么满的是另一块磁盘，或者是该磁盘拒绝写入大文件。这些情况各有专门的指南：WinRAR 提示磁盘空间不足，但空间明明够用和7-Zip 提示磁盘空间不足。

可以解压到其他磁盘吗？

可以。如果另一块磁盘（比如第二块内置硬盘或移动硬盘）有足够空间存放解压出的文件，这是最简单的办法。压缩包留在原处，只有目标磁盘需要空间。

  • WinRAR：打开压缩包，选择“解压到”（Extract To），然后选一个位于另一块磁盘上的文件夹。
  • 7-Zip：打开压缩包，选择“提取”（Extract），然后修改“解压到”（Extract to）。
  • Windows 自带功能（仅限 ZIP）：右键单击压缩包，选择“全部解压缩”（Extract All），然后点“浏览”（Browse）。

反过来也行。先把压缩包移到移动硬盘上，再从那里解压到内置磁盘，这样内置磁盘只需为文件留出空间。

开始之前，先确认移动硬盘的格式：在文件资源管理器中右键单击它，选择“属性”，查看“文件系统”。据 Microsoft 的说明（英文），FAT32 无法存放任何 4 GiB 或更大的单个文件；exFAT 和 NTFS 没有这个限制。

如何在 Windows 上释放空间？

使用“存储感知”（在“设置”中的“系统”、“存储”下），或者旧版的“磁盘清理”工具。两者都会删除临时文件以及 Windows 用不到的其他文件；Microsoft 的释放磁盘空间指南（英文）对每种工具都有说明。

也看看“下载”文件夹，里面可能有已经解压过的压缩包和已经运行过的安装程序。只有能腾出与解压后大小相当的空间，释放空间才能解决问题。接下来的两种办法需要的空间要少得多。

分卷压缩包可以边解压边删除已用完的分卷吗？

有时可以，但要手动操作。如果压缩包分成多个分卷，例如 game.part1.rar、game.part2.rar 或 game.7z.001、game.7z.002，解压程序会按顺序读取它们；一旦开始读取下一个分卷，读完的那个就不再需要了。删除它就能腾出它占用的空间。

这种做法很麻烦，而且有两个风险。你必须知道解压程序正在读取哪个分卷，而删得太早的分卷就再也找不回来了。如果之后解压失败（比如遇到损坏的分卷），不重新下载已删除的分卷就无法从头再来。只有在下载能够重新获取时才这样做。

HatchZip 会自动完成这一步：分卷 7z、ZIP 或 RAR 压缩包中的每个分卷，一旦其中的内容不再需要，就会被删除。在 2026-10-22 发布于 README 的测试中，一个分成 5 个 40 MB 分卷的 7z 压缩包解压出了 200 MB 的文件，磁盘占用最多为 210 MB。

能否解压时不再为压缩包本身留出空间？

可以，方法是就地解压。HatchZip 从压缩包的最后一个文件开始，依次解压到第一个文件；每一批文件安全写入后，就把压缩包文件末尾对应的那部分截掉。腾出的空间用来存放下一批文件，因此磁盘只需容纳解压出的文件再加一点余量，完成后只剩下解压出的文件。

它支持 ZIP、7z、tar、.tar.gz、.tar.bz2、.tar.xz、.tar.zst、RAR 和分卷压缩包，可在 Windows、macOS 和 Linux 上运行，免费且开源。下载 HatchZip。

代价是压缩包会被用掉。如果需要保留压缩包，应该使用普通解压，而普通解压需要完整的空间。

开始之前，怎样确认空间够不够？

对压缩包运行 hatchzip check。它会读取压缩包的索引和磁盘的可用空间，不做任何修改，并同时列出普通解压所需的空间和就地解压所需的空间。下面是对后文测试所用压缩包的检查结果，磁盘可用空间为 50.6 MB：

$ hatchzip check game.zip --keep-free 5M
game.zip  180.1 MB zip, 200.0 MB uncompressed in 22 entries
  available                    50.6 MB
  standard extraction needs    200.1 MB
  required                     28.6 MB (+5.0 MB reserved)
  available after              30.6 MB
  • “standard extraction needs”是 WinRAR、7-Zip 或 unzip 在这里所需的空间：200.1 MB，约为可用空间的四倍。
  • “required”是 HatchZip 在整个解压过程中任一时刻所需的最大可用空间，“available after”是解压完成后剩余的空间。
  • 空间不够时，check 会说明还差多少空间，并以退出码 3 退出。桌面应用会在你选择“解压”之前显示同样的数据。

HatchZip 默认保留 2 GB 可用空间，确保磁盘不会被完全占满。测试磁盘总共只有 220 MiB，所以用 --keep-free 5M 把预留空间降到了 5 MB。

实测：在几乎已满的磁盘上对比 unzip、7-Zip 和 HatchZip

测试日期 2026-10-25。方法：将 200.0 MB 的数据（共 21 个文件，主要是随机字节，因此几乎无法压缩）用 Info-ZIP Zip 3.0 打包成一个 180.1 MB 的 ZIP，再用 7-Zip 25.01 打包成两个 180.0 MB 的 7z 压缩包，其中一个使用 -ms=20m（分为多个固实块），另一个使用默认设置。每个压缩包分别单独复制到一块 220 MiB 的空磁盘上（复制后剩余 50.6 MB 可用空间），并解压到同一块磁盘。

7-Zip 25.01两个 7z 压缩包写入第 6 个文件（共 21 个）时中止：“No space left on device”

Fedora 43（Linux 6.19），Intel Core i7-14700HX。这块 220 MiB 的磁盘是 tmpfs，即放在内存中的磁盘，用来模拟一块已满的笔记本硬盘。HatchZip 运行时使用了 --keep-free 5M，原因见上文。ZIP 的结果与 2026-10-21 首次发布在 HatchZip README 中的结果一致。

HatchZip 适合什么情况，不适合什么情况

当压缩包和文件位于同一块磁盘，且磁盘放得下解压出的文件、但放不下两者时，就适合使用它。它还能代替你手动删除分卷。

以下情况它帮不上忙：

  • 磁盘连解压出的文件本身都放不下。这时只能换一块磁盘或更大的磁盘。
  • 压缩包是用 7-Zip 默认设置创建的 7z。这种压缩包可能是单个固实块，HatchZip 只有在整个固实块解压完后才能释放它，所以所需空间与普通解压差不多。hatchzip check 会事先告诉你，就像上面的测试那样。
  • 压缩包是固实 RAR。HatchZip 只能在保留压缩包的情况下解压它，因此需要完整的空间。
  • 问题出在 WinRAR 或 7-Zip 的临时文件夹，或者 FAT32 磁盘拒绝写入 4 GiB 或更大的文件。这些并不是磁盘空间不足；请参阅 WinRAR 和 7-Zip 的指南。
  • 你希望解压后保留压缩包。
  • 压缩包是用 zstd 命令创建的 .tar.zst，这种文件只有一个帧。HatchZip 只能在保留压缩包的情况下解压它，因此需要完整的空间。

文件解压出来的同时，压缩包也会被用掉。如果下载的文件已损坏，损坏位置之前的文件能解压出来，但压缩包已经部分删除；对于无法重新下载的文件，可以使用 --verify-first，它会在删除任何内容之前先读取整个压缩包。
